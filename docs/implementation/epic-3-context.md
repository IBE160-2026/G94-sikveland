# Epic 3 Context: Document checklist with saved ticks

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

An applicant picks a visit purpose (tourism, visiting family, visiting friends), gets a fixed, adviser-reviewed document checklist where every item links to an official source, ticks off the documents they already have, and finds the ticks still there days later on the same phone, with no account. This replaces asking the adviser to check documents one by one. The checklist is fixed data, never generated by the AI. The applicant can open it from a button that is always visible and from a button under answers that cite checklist-linked sources. The family checklist covers the sponsor's forms (sponsorship form and invitation letter), which is the edge case in the main user journey. In the build order this epic comes after the core (Epic 1) and Epic 2's fixed replies and feedback question (Stories 2.1–2.3), which are already built.

## Stories

- Story 3.1: Checklists per visit purpose
- Story 3.2: Tick off documents, and the ticks are kept
- Story 3.3: Open the checklist from the chat

## Requirements & Constraints

- **Fixed content.** One checklist per visit purpose. The texts are written in advance and never produced by the model. Building or serving a checklist makes no LLM call.
- **Every item has a source.** Each item links to a source in the knowledge base. UDI's official checklist remains the authority, and the app's checklist guides the applicant to it.
- **Family checklist.** It includes the sponsorship form and the invitation letter, says that the sponsor in Norway fills them in, and links to where the sponsor finds them.
- **Ticks stay on the device.** Ticks are kept between visits on the same phone and browser, with no account, and nothing about them is sent to or stored on the server.
- **Ticks survive content updates.** Ticks on unchanged items are kept, ticks for removed item IDs are ignored, and new items start unticked.
- **Mobile first.** The page works from 360 px wide with no horizontal scrolling down to 320 px. Checkboxes and buttons are at least 44×44 px. It must work in Facebook's in-app browser.
- **Adviser review.** All Thai checklist texts, and any new fixed Thai UI texts, are reviewed by the adviser before release and checked against UDI's official checklist.
- **Safe tests.** Tests use the scripted fake and never the real API. Story 3.3's tests cover answers both with and without checklist-linked sources.

## Technical Decisions

- **Data file:** `content/checklists.yaml` holds one checklist per purpose, keyed `tourism`, `family` and `friends` (snake_case, like the other category values). Each item has a stable lowercase kebab-case `id`, `th` and `en` text, and a source `id` from `knowledge-base/sources.yaml`. Item IDs must never be reused for different content, because the saved ticks depend on them.
- **Loading and startup checks:** `ContentStore` loads the checklists. The app refuses to start if an item refers to an unknown source `id` or if two items in one checklist share an `id`.
- **Endpoint:** `GET /api/checklists/{purpose}` returns the items in Thai, each with its `id`, text and source resolved to `{title, url}`. An unknown purpose returns 404 with the error envelope `{"error": {"code", "message"}}`.
- **Links:** every link shown must point to a source in `sources.yaml`. The app never fetches web pages at runtime. A new source (for example a sponsor form page) goes through the ingest and adviser-review path.
- **Tick storage:** `localStorage` key `checklist:{purpose}`, holding a list of ticked item IDs. When the page loads, it intersects the saved IDs with the current item IDs.
- **Stream contract extension (3.3):** the `sources` event already has `checklist` and `checklist_purposes` fields, currently always `false` and `[]`. Set `checklist: true` when any cited known source is linked to a checklist item. `checklist_purposes` lists every purpose whose checklist has an item linked to a cited source, and is empty when `checklist` is false. Fixed replies keep `checklist: false`. Only `app/web` builds stream events. The pipeline and adapters only supply source IDs.
- **No hard-coded Thai in the page:** every user-facing label (the Checklist button, Open checklist, the purpose choice, back) comes from content served to the page. New fixed text keys go into the closed key list in `content/texts.yaml` with `th` and `en`, and a missing key fails startup.
- **Errors:** if loading a checklist fails, the applicant sees the fixed `error` text.

## UX & Interaction Patterns

- A permanent "Checklist" button is always visible on the chat page.
- Opening the checklist starts with a choice of visit purpose. The page then shows that checklist, with a large checkbox and a source link on each item.
- Ticking or unticking an item saves at once, on the device only.
- Going back returns to the chat with the conversation unchanged. The open chat, its history and its stream state must not be reset.
- When an answer's `sources` event has `checklist: true`, an "Open checklist" button appears under that answer. With one purpose, it opens that checklist directly. With more than one, it opens the visit-purpose choice first.
- No UX design document exists. Layout is decided in the stories, within the mobile-first limits above.
- **Open point (not settled in planning):** saved chats store each exchange as `{question, answer, sources, reminder}`, without the checklist flags. Story 3.3 must decide whether "Open checklist" also appears under answers replayed from a saved chat. For comparison, the feedback buttons show only under live replies.

## Cross-Story Dependencies

- 3.1 provides the data, the startup checks and the endpoint. 3.2 builds the page view on that endpoint. 3.3 reuses 3.2's purpose choice and checklist view, and needs 3.1's item-to-source links to work out `checklist_purposes`.
- Epic 1 dependencies:
  - the knowledge base and `sources.yaml` (it already has the embassy checklist, UDI sponsor, sponsorship-form and invitation sources)
  - the stream contract and `sources` event from Story 1.6
  - the text loading through `GET /api/texts`
  - the page's saved-chats and view handling
- Epic 5's test set covers checklist questions, and demo answers that cite checklist-linked sources will show "Open checklist" in demo mode.
